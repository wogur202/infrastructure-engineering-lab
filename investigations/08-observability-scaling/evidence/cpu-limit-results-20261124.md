## 질문과 통제 조건

같은 요청률에서 CPU Limit을 높이면 CFS 제한과 응답 지연이 반복적으로 줄어드는지 확인했다. W=100000, 목표15RPS, CPU request250m, memory request/limit128/256Mi, Replica1, HPA OFF를 고정하고 CPU Limit만250m/1000m으로 바꿨다.

각 Trial은 warmup60초 → 측정180초 → 회복60초다. API와 k6는 서로 다른 역할의 Worker에 고정했다. 순서는250→1000 / 1000→250 / 250→1000이며, 같은 조건이 연속될 때도 부하 종료와 회복 후 새 Job으로 실행했다. 배포 전환과 warmup은 아래 지연·처리율 계산에서 제외했다.

CPU는 raw cAdvisor usage counter 증가량/표본 간 경과시간이다. CFS 기간 비율은 throttled periods 증가량/total periods 증가량이다. **CPU 사용률이나 요청 실패율을 뜻하지 않는다.** 제한 시간 증가도 HTTP 지연의 합계가 아니다.

Prometheus scrape 설정은15초지만 cAdvisor의 실제 원시 시각은 불규칙했다. measure 태그의 첫 응답 종료 시각에서 그 응답 지연을 뺀 시각을 측정 시작의 근사값으로 두고, 그180초 내부의 실제 원시 표본만 사용했다. 따라서 위CPU/CFS는152.646~167.193초의 내부 표본 차이이며 전체180초 평균으로 외삽하지 않았다. 사용한 구간에서 counter reset이나45초 초과 표본 간격은 없었다. 기존2분 rate만으로60초Pilot과 본실험을 섞어 해석하지 않았다.

## 반복 결과의 해석

1. 250m에서는 세 번 모두 CFS 제한을 관측했고,1000m에서는 세 번 모두 표본 내 증가가0이었다. CPU 사용량은약218~221m로 비슷했다. 평균CPU가 limit보다 낮아도 개별 CFS 기간의 제한이 없다고 할 수는 없었다.
2. p95는 세 쌍 모두1000m 쪽이 낮았지만, 차이는21.644ms /16.263ms /0.045ms였다. 마지막 쌍은 사실상 비슷한 수준이다. 세 쌍의 방향만으로 일정한 개선율이나 강한 인과효과를 확정하지 않는다.
3. T4와T5의 CFS 기간 비율은약51.4%와50.1%로 비슷하지만 p95는31.934ms와15.874ms였다. 제한 시간 증가량도2.665196초와0.602985초로 달랐다. 기간 비율 하나로 제한의 강도나 지연을 설명하면 안 된다. 남은 변동의 원인을 이번 측정만으로 특정하지 않았다.
4. 두CPU Limit 모두 목표 요청률을 달성했다. **처리량 향상을 입증한 결과는 아니다.** 250m에서는 처리 불가능하고1000m에서만 가능한 안정적인 부하 구간도 찾지 못했다.

## 유효성 및 세션 분리

모든 본실험 Trial에서 추가API 재시작0, 새로 발생하거나 횟수가 증가한 Probe 경고0, Node Pressure0이었다. 노드 UID/providerID와 실제 배치를 대조했다. Prometheus Target은 각 수집 구간에서 모두Up이었고 필수CPU/CFS 시계열이 존재했다. k6CPU는약15.25~15.78m, 메모리 최대약16.89~17.05MiB였고 표본 내 k6 CFS 증가는0이었다. 목표 요청률을 유지했으며 발생기 CPU포화 증거는 없었다.

T1·T2는11월23일, T3~T6는11월24일(KST)에 수행했다. T2측정 종료와T3측정 시작 사이 간격은약9.09시간이다. 중단 없는6회 연속 실험으로 표현하지 않는다. 재개 전 노드2대와 API Pod의UID, 이미지·자원 설정이 같고 Ready·Metrics가 정상임을 확인했지만, 시간대별 호스트 간섭이나 스케줄링 조건까지 완전히 같았다고 보장할 수 없다.

AWS CLI 인증 만료는 기존terraform-lab으로 재인증했고 종료된 localhost Prometheus 연결만 복구했다. 초기 본실험 전 Metrics API 조회1건은30초 timeout 후 재조회·preflight가 통과했다. 이러한 재개·조회 실패와 당시 로그도 비공개로 남겼다. IAM 확대나 인프라 재생성으로 해결하지 않았다.
