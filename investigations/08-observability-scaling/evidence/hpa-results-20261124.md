# HPA OFF/ON 본실험 결과 — 2026-11-24

8-D-2는 **HPA 기능 검증 PASS, 관측 환경의 한계를 명시한 조건부 PASS**로 정리했다.
HPA는 세 번 모두 1→2→1로 동작했고 CPU 부하를 분산했다. 이번 부하에서는 1개 Pod도
목표 요청을 처리했으며, HPA의 처리량 증가나 응답 지연 개선은 확인하지 못했다.

## 1. 조건과 실행 순서

- W=100000, 목표 30 RPS, warm-up 60초 + 측정 240초.
- API request=limit 500m, memory request/limit 128/256Mi.
- OFF는 1개 고정, ON은 min1/max2, CPU target70%, 축소 안정화300초.
- 같은 STEP08 이미지 digest, 같은 기존 API Pod UID, 같은 두 Node UID/providerID를 확인했다.
- API는 api 역할 Worker, k6는 support 역할 Worker에 배치했다. 두 API Pod는 같은 Worker에서 실행했다.
- 순서는 OFF→ON / ON→OFF / OFF→ON이다. 매번 기존 부하 종료와 회복을 확인했고 ON은 1개 Ready에서 시작했다.
- 실행 중 k6 내부 진단을 하지 않았다. 부하 종료 후 기존 collect.py로 raw·summary·Kubernetes·Prometheus 증빙을 수집했다.

서비스 복구 시간이나 AWS 리소스 생성 시간을 뜻하지 않는다.

watch가 전체 시간 동안 끊김 없이 유지됐다고 주장하지 않는다. 회복 중에도 외부 snapshot과 Prometheus 수집을 계속했다.
축소 중에는 부하를 주지 않았으므로 축소 과정의 무중단 처리를 검증한 것은 아니다.

k6 CPU limit는400m이며 평균은20.4~24.9m, 내부 표본의 CFS counter 증가는0이었다.
목표 RPS·오류·Drop·CPU 여유를 함께 확인했으며 CFS가0이라는 사실만으로 발생기 정상 여부를 판단하지 않았다.

확장 전·전환 중·두 Ready 이후 구간은 warm-up을 포함한 설명용 구간이다.
안정 구간만 두 Ready와 유효 Metrics 확인 이후의 measure 구간으로 잘랐다.

전환은1/5/1초로 짧았고 요청30/150/30건에서 일시적인 지연 증가가 관측됐다.
이 표본으로 전환 지연의 일반적인 백분위나 성능 개선율을 확정하지 않는다.
전환 중 CPU는 scrape 간격보다 구간이 짧아 유효 counter delta를 계산할 표본이 부족했다.
확장 전 CPU도 약26~31초의 짧은 내부 표본에서427~434m가 관측됐으므로 설명용으로만 썼다.
요청 구간은 duration 종료 timestamp−duration으로 근사했으며 연결 수립 시간은 포함하지 않아 경계에 오차가 있다.

새 Pod가 최초 Ready 되기 전 Readiness 경고는 ON별1/2/1건이었다.
최초 Ready 이전 이벤트와 이미 서비스를 제공하던 Pod의 장애를 구분했다.
기존 Pod의 Ready 상실·재시작과 HTTP 실패는 없었지만, 이를 모든 부하의 무중단 보장으로 확대하지 않는다.

## 5. 관측 환경 한계와 기존 중단 기준

기존 [README 4절](../README.md)의 기준은 다음과 같으며 이번 정리에서 바꾸지 않았다.

> 생성기/관측기 지속 CFS, scrape 누락, node pressure, Pending, 예상 밖 restart, 비용·시간 초과가 있으면 중단·무효 사유를 기록한다.

최종 검토에서 node-exporter의 지속적인 CFS 제한을 발견했다. 실행 중 이 항목을 즉시 판정하지 못했으므로
원래 관측기 품질 기준을 모두 통과했다고 할 수 없다. 단순 PASS로 처리하지 않고 기준 적용의 차이를 남긴다.

이는2분 rate의 조회 표본 최대값이다. CFS period 비율은 CPU 사용률이나 손실된 CPU 시간의 비율이 아니다.
node-exporter 평균 CPU는 약0.6~1m/limit50m로 낮았지만 제한이 실제 발생한 사실은 남긴다.
Operator 등 일부 관측 컨테이너에도 소량의 CFS가 있었고 Prometheus 자체 CFS는0이었다.
11개 target은 모든 수집 구간에서 Up이었고, API/k6 CPU의 주 근거는 node-exporter가 아닌 kubelet cAdvisor 원시 counter다.
따라서 HPA 기능·HTTP 성공·CPU 분산의 근거는 유지하되, 관측 환경의 영향이 전혀 없다고 증명한 것은 아니다.
미세한 지연 차이는 제한적으로 해석하며 전체 판정은 **조건부 PASS**로 남겼다.
이 판정은 결과를 본 뒤 기존 기준을 조용히 완화한 것이 아니라, 원래 기준을 충족하지 못한 사실과 사후 검토를 공개한 것이다.
추가 실험이나 node-exporter 자원 변경은 하지 않았다.

## 6. 참고용으로 분리한 최초 OFF

최초 실행 hpa-t1-off-231417은 측정7,202건 모두200,30.00833RPS,p95 15.728ms로 정상 종료했다.

그 시점과 CFS counter 증가가 겹쳤지만 정확한 인과관계는 확정하지 않았다.
